## เป้าหมายของโปรเจกต์ (อ่านก่อนทุกครั้ง)

> **จำลองว่าเมื่อเกิดเหตุการณ์หนึ่งขึ้น _สังคมไทย_ จะมีความเห็นอย่างไร และจะ _มีพฤติกรรม_ แบบไหน**
>
> ขอบเขตคือ **สังคม ไม่ใช่แค่ชาวเน็ต** — โซเชียลมีเดียเป็นเพียงหนึ่งในช่องทางรับรู้
> และการโพสต์เป็นเพียงหนึ่งในพฤติกรรมที่เป็นไปได้

ผลที่ตามมาต่อการออกแบบ (ห้ามลืม):

1. **คนที่ไม่โพสต์คือคนส่วนใหญ่ และเขามีน้ำหนักเต็ม** — เขาไปเลือกตั้ง เลิกซื้อของ
   ต่อคิวถอนเงิน กักตุนของ "นิ่งเฉย" จึงไม่ใช่ผลลัพธ์ว่าง แต่คือ "มีความเห็นแล้วแต่ไม่แสดงออก"
2. **ต้องแยก `private_opinion` ออกจาก `public_expression`** — ดูหัวข้อ C1 ด้านล่าง
3. **ประชากรต้องสุ่มจากคนทั้งสังคม** ไม่ใช่จากผู้ใช้โซเชียล มิฉะนั้นตัวอย่างเอียงไปทาง
   คนอายุน้อย/ในเมืองทันที
4. **ช่องทางข่าวสารมีหลายชั้น** ไม่ใช่ฟีดอย่างเดียว — ทีวี, กลุ่ม LINE, ปากต่อปาก,
   ผู้นำชุมชน แต่ละช่องมีคนเข้าถึงต่างกันและความน่าเชื่อถือต่างกัน
5. **ตัววัดต้องเป็นการกระจายความเห็นและอัตราการเกิดพฤติกรรม** ไม่ใช่ยอดโพสต์/ยอดแชร์

## C1. แก่นของงานวิจัย: ช่องว่างระหว่าง "สิ่งที่คิด" กับ "สิ่งที่พูด"

`fear_level` ที่เขียนไว้แล้วใน `core/agent.py` (คอมเมนต์ว่า *"หวาดระแวงการโดนฟ้อง"*)
มีความหมายก็ต่อเมื่อ agent มีสองชั้นนี้เท่านั้น — เพราะความกลัว**ไม่เปลี่ยนสิ่งที่คนคิด
แต่เปลี่ยนสิ่งที่คนกล้าพูด**

```text
private_opinion   ── สิ่งที่เชื่อจริง (เปลี่ยนตามข้อมูล + อิทธิพลคนรอบตัว)
       │
       ├── expression_filter ← fear, เกรงใจ, ระบบอาวุโส, บริบทของช่องทาง
       ↓
public_expression ── สิ่งที่แสดงออก (อาจเงียบ / อ้อม / ตรงข้ามกับที่คิด)
```

**ทำไมถึงเป็น contribution:** โมเดลที่ดูแค่โซเชียลมองเห็นได้แค่ชั้นล่าง แล้วสรุปผิดว่า
"สังคมเห็นด้วย" ทั้งที่จริงคือ "สังคมไม่กล้าพูด" — ในไทยช่องว่างนี้กว้างเป็นพิเศษและ
เป็นสาเหตุที่โพลกับผลจริงมักไม่ตรงกัน

**สิ่งที่ต้องบันทึกทุกรอบ:** ทั้งสองชั้น + ขนาดช่องว่าง (`preference falsification`)

| กลุ่ม | ตัวอย่าง |
|---|---|
| **ออนไลน์ สาธารณะ** | โพสต์, แชร์, คอมเมนต์, เลี่ยงบาลี (พูดอ้อมเพื่อเลี่ยงความเสี่ยง) |
| **ออนไลน์ ปิด** | ส่งต่อในกลุ่ม LINE ครอบครัว/ที่ทำงาน (ไว้ใจสูง วัดยอดไม่ได้) |

## C4. ปิด reasoning แล้วหลอนมั้ย + ทำไม expression_filter ต้องเป็นโค้ด

วัดด้วย `backend/scripts/eval_reasoning_effect.py` (36 calls, `qwen3-30b-a3b-instruct-2507`)
งานนี้ไม่มีคำตอบถูก จึงวัด 4 อย่างที่มีความหมายกับการจำลองสังคมแทน

| ตัววัด | ปิด reasoning | เปิด reasoning |
|---|---|---|
| GROUNDING ใช้ความทรงจำที่ป้อนให้ | **2.67 / 3** | 2.56 / 3 |
| INVENTION แต่งตัวเลขที่ไม่ได้ให้ (= หลอนของจริง) | **ไม่มี** | **ไม่มี** |
| DIVERSITY entropy ของ action | **0.99** | 0.85 |
| MECHANISM fear ต่ำ → fear สูง | +0.17 | +0.33 |

**สรุปเรื่องการหลอน: ปิด reasoning ไม่ได้ทำให้หลอนขึ้น** ไม่มีการแต่งข้อมูลในทั้งสองเงื่อนไข
และ grounding ไม่ได้แย่ลง ส่วนที่เปิด reasoning ทำได้ดีกว่าคือกลไก fear เล็กน้อย
แต่แลกด้วย**ความหลากหลายที่ลดลง** (มันลากทุก agent ไปหาคำตอบที่ "สมเหตุสมผลที่สุด"
ซึ่งทำลาย variance ที่งานจำลองประชากรต้องการ)

> ⚠️ N=18 ต่อเงื่อนไข persona เดียว เหตุการณ์เดียว — ความต่าง 0.17 vs 0.33 อยู่ในช่วง noise
> ยังไม่ควรสรุปแน่นหนา แต่ทิศทางชัดพอจะออกแบบต่อได้

### ปัญหาที่ใหญ่กว่า: LLM ไม่ตอบสนองต่อค่า `fear` เลย

```text
เลือก action จาก 6 ตัวเลือก (18 ครั้ง):
  ปิด reasoning : {ส่งในกลุ่มไลน์: 10, คุยกับคนในบ้าน: 8}   ← ไม่เคยเลือก "เงียบ" เลย
  เปิด reasoning: {ส่งในกลุ่มไลน์: 13, คุยกับคนในบ้าน: 5}
```

`fear=15` กับ `fear=85` ให้ผลเกือบเท่ากัน (2.67 vs 2.50)

**ลองแก้ด้วยการบอกกติกาชัดเจนใน prompt → แย่ลงกว่าเดิม:**

| | fear=15 | fear=50 | fear=85 |
|---|---|---|---|
| ไม่บอกกติกา | ไลน์ 5 / เงียบ 3 | ไลน์ 4 / เงียบ 4 | ไลน์ 4 / เงียบ 4 |
| บอกกติกาชัดเจน | **เงียบ 8/8** | **เงียบ 8/8** | **เงียบ 8/8** |

การบอกกติกาทำให้ยุบเหลือคำตอบเดียวทุกระดับ — เปลี่ยนจาก "ไม่สนใจ fear"
เป็น "ไม่สนใจ fear แล้วเลือกทางปลอดภัยสุดอย่างเดียว"

อีกข้อสังเกต: แค่ตัดฟิลด์ `private_opinion`/`reason` ออกจากสคีมา การกระจาย action ก็เปลี่ยนไปแล้ว
→ **ผลลัพธ์ไวต่อรูปแบบ prompt มากกว่าไวต่อตัวแปรที่เราตั้งใจศึกษา**
ซึ่งเป็นเรื่องใหญ่ต่อความน่าเชื่อถือของงาน

### ผลต่อการออกแบบ (D10)

**ห้ามให้ LLM ตัดสินว่า "กลัวเท่านี้แล้วกล้าพูดแค่ไหน"** แบ่งหน้าที่ใหม่:

```text
LLM  ──> private_opinion         (สิ่งที่คิด — LLM เก่งเรื่องนี้)
โค้ด ──> expression_filter        (fear + persona + ช่องทาง -> ชุด action ที่เป็นไปได้ + น้ำหนัก)
LLM  ──> public_content           (เขียนข้อความ ตาม action ที่โค้ดเลือกมาแล้ว)
```

ข้อดี: กลไกตรวจสอบได้ ปรับจูนได้ อธิบายในวิทยานิพนธ์ได้ และ **reproduce ได้**
ต่างจากการฝากไว้กับอารมณ์ของ LLM ซึ่งพิสูจน์แล้วว่าไม่ตอบสนอง

ผังใน C1 วาดถูกมาตั้งแต่แรก — `expression_filter` เป็นกล่องแยกนอก LLM อยู่แล้ว

## C5. เกรงใจเป็นเรื่อง "ความสัมพันธ์" ไม่ใช่คุณสมบัติของคน

ตอนออกแบบครั้งแรกใส่ `deference` เป็นค่าเดียวของแต่ละคน แล้วเอาไปกดทุก action เท่ากัน
ซึ่งผิดธรรมชาติของเกรงใจไทย — คนคนเดียวกันบ่นที่บ้านได้ แต่เงียบกริบต่อหน้าหัวหน้า

จึงแยกแรงกดเป็นสองชนิด:

| แรงกด | ขอบเขต | เหตุผล |
|---|---|---|
| **กลัวคดี** (`legal_fear`) | กดทุกช่องทางเท่ากัน | โพสต์ผิดในกลุ่มไลน์ก็โดนได้เหมือนโพสต์สาธารณะ |
| **เกรงใจ/อาวุโส** (`social_pressure`) | กดตาม `Action.deference_weight` | ขึ้นกับว่ากำลังเผชิญหน้ากับใคร |

`deference_weight` ต่อการกระทำ: ปรึกษาผู้นำชุมชน 1.9 · คุยกับเพื่อนร่วมงาน 1.7 ·
ร้องเรียนหน่วยงาน 1.2 · ส่งในกลุ่มไลน์ 0.9 · คุยกับคนในบ้าน 0.5 · **เลี่ยงบาลี 0.25** ·
พฤติกรรมส่วนตัว (แบน/กักตุน/ถอนเงิน) 0.0

และเพิ่ม `situational_deference` (0–2) สำหรับสถานการณ์ เช่น เรื่องกระทบที่ทำงานตัวเอง (1.8)
หรือใช้บัญชีนิรนาม (0.1)

**ผลที่ได้น่าสนใจกว่าที่ออกแบบไว้** — คนเกรงใจสูง (เทียบกับเกรงใจต่ำ ที่ `fear` เท่ากัน):

| การกระทำ | เปลี่ยน |
|---|---|
| ปรึกษาผู้นำชุมชน | −61% |
| คุยกับเพื่อนร่วมงาน | −55% |
| ร้องเรียนหน่วยงาน | −46% |
| คุยกับคนในบ้าน | **+25%** |
| เลี่ยงบาลี | **+30%** |
| เลิกซื้อ/แบน | **+43%** |

**เกรงใจไม่ได้ทำให้คนเงียบหายไป แต่ผลักคนไปช่องทางที่ไม่ต้องเผชิญหน้า**

### C7. บทเรียนจากการรันเคสจริง (PARAMETER, 2026-08-02)

ลองรันเคสร้านเจลาโต้ 20 agent × 6 รอบ = 95 การตอบสนอง **นอกกรอบที่ออกแบบมา**
(action space เดิมออกแบบจากเหตุการณ์การเมือง) แล้วเจอข้อบกพร่องที่เทสต์ 197 ตัวจับไม่ได้

| ข้อบกพร่อง | หลักฐาน | แก้แล้วยังไง |
|---|---|---|
| **ไม่มี action ฝั่ง "เข้าร่วม"** | มีแต่ประท้วง/ร้องเรียน/ถอนตัว จำลอง "ยิ่งด่ายิ่งขายดี" ไม่ได้เชิงโครงสร้าง | เพิ่ม `buy_anyway` / `show_off` / `defend_public` |
| **action ไม่ผูกกับเหตุการณ์** | ไปม็อบ 3 / ถอนเงิน 3 / กักตุน 2 = **15/95 (16%)** ในเรื่องไอศกรีม | `core/scenario.py` จำกัด action ตามชนิดเหตุการณ์ |
| **`stance` ไม่มีที่อ้างอิง** | ได้ `supportive/75` ที่โกรธ 60 แล้วไปแบนร้าน — ตีความไม่ได้ | `Scenario` บังคับระบุ `subject` / `support_means` / `oppose_means` |
| **ทุกคนรู้ข่าวหมด** | ลุงอายุ 67 ลำปาง ไม่เล่นโซเชียล จบที่ `supportive/55` แล้วไปแบนร้าน | ⏳ ต้องรอ Phase 5 |
| **fear ปรับจูนมาสำหรับการเมือง** | fear 60–72 กับเรื่องไอศกรีมที่ไม่มีความเสี่ยงทางกฎหมายเลย | ⏳ ยังไม่แก้ |

**บั๊ก concurrency ที่เจอพ่วง** — รันครั้งแรกพังทั้ง 20 ตัว เพราะ singleton แบบ lazy
ใน Phase 2 ไม่มี lock และ `broadcast_event_async` ยิงพร้อมกัน 30 เธรด
ที่ร้ายที่สุดคือเรียก `.encode()` พร้อมกันแล้ว **segfault ที่ `modeling_bert.py forward`**
เทสต์จับไม่ได้เพราะรันทีละตัว → เพิ่ม `test_concurrent_agents_can_use_memory`

> **บทเรียนเชิงวิธีการ:** เทสต์ที่ผ่านหมดไม่ได้แปลว่าโมเดลถูก — ต้องรันเคสที่
> *อยู่นอกกรอบที่ออกแบบมา* ถึงจะเห็นสมมติฐานที่ฝังอยู่ นี่คือเหตุผลที่ควรมี
> **สองเคสคนละโดเมน** (ดราม่าผู้บริโภค + ภัยพิบัติ/การเมือง) ไม่ใช่เคสเดียว

### C8. เทียบกับ OASIS: อะไรลอกได้ อะไรลอกไม่ได้

อ่านโค้ด OASIS จริงเพื่อดูว่าเขาแก้ปัญหาเดียวกันยังไง

| ปัญหา | OASIS ทำยังไง | เรา |
|---|---|---|
| ซื้อ/เข้าร่วม | มี `PURCHASE_PRODUCT` + `JOIN_GROUP` — **แต่ MiroFish เปิดใช้แค่ 6 action ไม่รวมตัวนี้** | ✅ ลอก |
| action ไม่เข้าเรื่อง | `available_actions` → แปลงเป็น**รายการ tool ที่ส่งให้ LLM** ตัวที่ไม่อยู่ในลิสต์โมเดลมองไม่เห็น | ✅ ลอกแนวคิด |
| `stance` | **ไม่มี stance/emotion/fear เลยทั้ง package** ความเห็นอยู่ในข้อความที่ generate แล้วนับย้อนหลัง | ❌ ลอกไม่ได้ — ชั้นความเห็นในใจคือสิ่งที่เราเพิ่ม |
| ใครรู้ข่าว | `rec_matrix` + `max_rec_post_len=2` เห็นแค่ ~2 โพสต์/รอบ | ⚠️ ลอก pattern แต่ต้องขยายเป็นหลายช่องทาง (ทีวี/ไลน์/ปากต่อปาก) |

> ข้อ `stance` ยืนยันว่างานนี้ไม่ได้ทำซ้ำของเดิม — OASIS **ตอบไม่ได้**ว่า
> "คิดแบบนี้กี่ % แต่กล้าพูดกี่ %" เพราะไม่มีชั้นความเห็นในใจให้วัด

### C6. ทำไม `app/` กับ `core/` อยู่ด้วยกันได้ (ตรวจโค้ดแล้ว)

`SimulationRunner.start_simulation()` **เลือกสคริปต์ตาม platform** แล้วเปิดเป็น subprocess:

```python
script_name = "run_twitter_simulation.py"   # หรือ reddit / parallel
process = subprocess.Popen([...])
```

จากนั้นคุยกับมันผ่าน "สัญญา" แค่ 3 อย่าง ซึ่งเป็นไฟล์ล้วน ๆ:

1. **อ่านเข้า** — `simulation_config.json` + profiles CSV ในโฟลเดอร์ของ simulation
2. **เขียนออก** — `{sim_dir}/{platform}/actions.jsonl` หนึ่งบรรทัดต่อหนึ่ง action
   (`round, timestamp, agent_id, agent_name, action_type, action_args, result, success`)
3. **ตอบ interview** — วน `SimulationIPCServer.poll_commands()` อ่านไฟล์คำสั่ง

**แปลว่าเพิ่มสคริปต์ `run_thai_society_simulation.py` ที่ขับ `core.PlatformHub`
แล้วเคารพสัญญา 3 ข้อนี้ ก็เสียบแทน OASIS ได้โดย _ไม่ต้องแก้ `app/api/`, frontend, หรือ report layer เลย_**

และ `action_args` เป็น dict อิสระ จึงใส่สองชั้นลงไปได้ตรง ๆ:

```json
{"action_type": "SILENT_SHIFT",
 "action_args": {"content": null, "private_stance": "oppose", "private_intensity": 78,
                 "fear": 71, "anger": 64, "channel": "line", "chosen_exposure": 0.0}}
```

นี่คือเหตุผลที่ D6 (log เป็น `actions.jsonl`) ตัดสินใจถูกตั้งแต่แรก และทำให้
`trace_statistics` ที่แก้ไปแล้วอ่านชั้น private ได้ทันที

> ✅ **ขอบเขต "สังคม" ยิ่งยืนยันว่าต้องมี engine ของตัวเอง**: OASIS เป็น simulator ของ*แพลตฟอร์มโซเชียล*โดยเฉพาะ
> โครงสร้างมันไม่มีที่ให้ความเห็นที่ไม่ถูกแสดงออก และไม่มีที่ให้พฤติกรรมออฟไลน์เลย
> **ข้อแลกเปลี่ยน:** เราต้องสร้าง feed / recsys / follow graph เองใน Phase 4 ซึ่งจะได้ไม่ครบเท่า OASIS
> แลกกับการได้โมเดลที่ตอบคำถามวิจัยได้จริง — แต่ **ไม่ต้อง**เขียนเปลือกแอปใหม่ เพราะยืมของ MiroFish ได้ทั้งดุ้น

## Phase 1 — โมเดล Agent ให้เป็น "คนในสังคม" ไม่ใช่ "ผู้ใช้โซเชียล"

**เป้า:** agent มีความเห็นส่วนตัวแยกจากสิ่งที่แสดงออก และทำอะไรได้มากกว่าโพสต์
**ขนาด:** 1–2 วัน — **เป็นรากของทุกเฟสถัดไป ทำผิดตรงนี้แล้วต้องรื้อทั้งหมด**

| # | งาน | หมายเหตุ |
|---|---|---|
| 1.1 | เพิ่ม `private_opinion` (จุดยืน + ความเข้มข้น + ความมั่นใจ) ใน `AgentState` | ชั้นที่คนอื่นมองไม่เห็น |
| 1.2 | **เขียน `expression_filter` เป็นโค้ด** (ตาม **D10**) — รับ `fear`, เกรงใจ, อาวุโส, ช่องทาง → คืนชุด action ที่เป็นไปได้พร้อมน้ำหนัก | **ห้ามฝากไว้กับ prompt** วัดแล้ว LLM ไม่ตอบสนองต่อ `fear` เลย ดู C4 |
| 1.3 | ขยาย action space ตามตาราง **C2** (ออนไลน์เปิด / ออนไลน์ปิด / ออฟไลน์คุย / ออฟไลน์ลงมือ / เปลี่ยนใจเงียบ) | |
| 1.4 | แยกการเรียก LLM เป็น 2 จังหวะ: (ก) ขอ `private_opinion` (ข) โค้ดเลือก action แล้วขอให้ LLM เขียน `public_content` ตาม action นั้น | ต้องได้ทั้งสองชั้นทุกครั้ง แม้ action = เงียบ |
| 1.5 | เพิ่ม `media_access` ใน `AgentProfile` — ใช้โซเชียลมั้ย / ดูทีวี / อยู่กลุ่ม LINE ไหน | ตัวกำหนดว่ารับข่าวจากช่องทางไหนได้บ้าง |

**เกณฑ์ผ่าน:**
- agent ที่ `fear_level` สูง ต้องเกิดกรณี **`private_opinion` = ต่อต้าน แต่ `public_expression` = เงียบ/อ้อม** ได้จริง
- agent ที่ไม่ใช้โซเชียลเลย ต้องยังมี `private_opinion` เปลี่ยนได้ และยังทำ action ออฟไลน์ได้
- ทุกรอบต้อง log ทั้งสองชั้น ไม่ใช่แค่สิ่งที่โพสต์
- **รัน `eval_reasoning_effect.py` แล้วค่า MECHANISM ต้องต่างกัน > 1.0** ระหว่าง fear ต่ำกับ fear สูง
  (ตอนนี้ได้แค่ 0.17–0.33 ซึ่งถือว่ากลไกไม่ทำงาน) — เกณฑ์นี้คือตัวพิสูจน์ว่า D10 แก้ปัญหาได้จริง
- action ที่เกิดขึ้นต้องกระจายมากกว่า 2 แบบ (ตอนนี้กระจุกอยู่แค่ ไลน์/คุยในบ้าน)

`thai_nlp_processor.py` มีแค่ 133 บรรทัด

| # | งาน | ออกที่ไหน |

## Phase 4 — ประชากรสังเคราะห์ = ภาพแทน "สังคม" (Task 2 ในเอกสาร)

**เป้า:** ประชากรที่เป็นตัวแทนคนไทยทั้งสังคม **ไม่ใช่แค่คนเล่นโซเชียล**
**ขนาด:** 2 วัน

| # | งาน |
|---|---|
| 4.1 | สคริปต์ `scripts/bootstrap_population.py` — LLM สร้าง persona ไทย + ประวัติย้อนหลัง |
| 4.2 | **สุ่มจากประชากรทั้งประเทศตามข้อมูล NSO** (อายุ/อาชีพ/ภูมิภาค/รายได้/การศึกษา) |
| 4.3 | **ใส่ `media_access` ให้ครบทุกแบบ** — คนที่ไม่แตะโซเชียลเลยต้องมีอยู่ในกลุ่มตัวอย่างตามสัดส่วนจริง |
| 4.4 | ประวัติย้อนหลังไม่ใช่แค่ "โพสต์" — รวมความเชื่อ/ประสบการณ์/เรื่องเล่าที่ได้ยินมา (คนไม่โพสต์ก็ต้องมีความจำ) |

**เกณฑ์ผ่าน:**

- **มี agent ที่ `media_access` ไม่มีโซเชียลเลย** ตามสัดส่วนจริง (ถ้าไม่มี = ตัวอย่างเอียง)

> ⚠️ ตัวเลข NSO ยังต้องหามาเอง — ระหว่างยังไม่มี ให้ใส่ค่าประมาณไว้ก่อนแต่**เขียนกำกับให้ชัดว่าเป็นค่าชั่วคราว** จะได้ไม่เผลออ้างอิงในรายงาน

## Phase 5 — เครือข่ายหลายชั้น + ช่องทางข่าวสาร (Task 3)

**เป้า:** ข่าวและอารมณ์เดินทางตามท่อจริงของสังคม ไม่ใช่กระจายเท่ากันทุกคน
**ขนาด:** 2–3 วัน

ตอนนี้ `environment.py` เขียนคอมเมนต์ยอมรับไว้เองว่า *"สมมติ Network Graph เป็น Fully Connected"* — ทุกคนเห็นทุกคนเท่ากัน ซึ่งทำให้ไม่มี echo chamber ไม่มีขั้ว และไม่มีความต่างระหว่างคนเมืองกับคนชนบท

**5A — เครือข่ายหลายชั้น** (คนหนึ่งคนอยู่ในหลายเครือข่ายพร้อมกัน)

| ชั้น | ลักษณะ |
|---|---|
| ออนไลน์สาธารณะ | กว้าง เร็ว อ่อนแอ (Twitter/FB) |
| กลุ่มปิด (LINE) | แคบ ไว้ใจสูง ตรวจสอบยาก |
| ครอบครัว / ที่ทำงาน | เล็ก อิทธิพลสูงมาก ข้ามรุ่นและข้ามขั้วได้ |
| ชุมชน / ผู้นำท้องถิ่น | สำคัญมากในต่างจังหวัด |

**5B — ช่องทางข่าวสาร** — ทีวี / โซเชียล / LINE / ปากต่อปาก แต่ละช่องมีคนเข้าถึงต่างกัน
ตาม `media_access` และ**ความน่าเชื่อถือต่างกัน** (ข่าวจากญาติในไลน์ ≠ ข่าวจากคนแปลกหน้าในทวิตเตอร์)

| # | งาน |
|---|---|
| 5.1 | สร้างกราฟหลายชั้นด้วย `networkx` — homophily จาก stance + region + อายุ + ที่ทำงาน |
| 5.2 | ชั้นครอบครัว/ที่ทำงาน **ต้องเชื่อมข้ามขั้วและข้ามรุ่น** (ไม่ใช่ homophily ล้วน) ไม่งั้นสังคมจะแตกเป็นเกาะสมบูรณ์ซึ่งไม่จริง |
| 5.3 | `calculate_network_contagion()` คิดจากเพื่อนบ้านในแต่ละชั้น + ถ่วงน้ำหนักตามความไว้ใจ |
| 5.4 | ข่าวแพร่ตามช่องทาง ไม่ใช่ broadcast — คนไม่มีโซเชียลต้องรู้ข่าวช้ากว่าและผ่านคนอื่น |
| 5.5 | ถ่วงน้ำหนัก influence (KOL / ผู้นำชุมชน แพร่แรงกว่า) + `random.seed()` |

**เกณฑ์ผ่าน:**
- วัด **modularity** ในชั้นออนไลน์ได้ > 0.3 แต่ชั้นครอบครัว**ต้องต่ำกว่า** (เชื่อมข้ามขั้ว)
- ทดลอง: ยิงข่าวเข้าเฉพาะโซเชียล → คนที่ไม่มีโซเชียลต้อง**รู้ทีหลัง**และผ่านคนกลาง ไม่ใช่รู้พร้อมกัน
- ยิงข่าวเข้า cluster เดียว → อารมณ์ขึ้นใน cluster นั้นก่อนแล้วค่อยลาม
- รันซ้ำด้วย seed เดิม → กราฟเหมือนเดิม

## Phase 7 — Protocol กัน leakage + Correspondence 3 ระดับ (**O4**, Task 4)

**เป้า:** ผลลัพธ์เอาไปเขียนรายงานได้โดยไม่โดนตั้งคำถาม
**ขนาด:** 3–4 วัน — **ข้ามไม่ได้ถ้าจะใช้ในวิทยานิพนธ์**

**7A — correspondence 3 ระดับ** (objective เขียนไว้ตรงตัวว่า *content, population, dynamic*)

| ระดับ | คำถาม | วัดยังไง |
|---|---|---|
| **Content** | ข้อความที่ agent เขียน อ่านเหมือนคนไทยเขียนจริงมั้ย | เทียบการกระจายความยาว/คำ/ระดับภาษา/สแลง กับคลังจริงจาก Phase 3 + ให้คนไทยแยกของจริงกับของจำลอง (ควรแยกไม่ค่อยออก) |
| **Population** | ประชากรจำลองเหมือนสังคมไทยมั้ย | เทียบสัดส่วน อายุ/ภูมิภาค/อาชีพ/`media_access` กับ NSO — และเทียบ **การกระจาย stance ตั้งต้น** กับผลโพลก่อนเหตุการณ์ |
| **Dynamic** | ความเห็นเปลี่ยนไปในทิศทางเดียวกับของจริงมั้ย | เทียบเส้นเวลาความเห็นกับผลโพลหลายจุดเวลา — ดู**ทิศทางและลำดับ** ไม่ใช่ค่าสัมบูรณ์ |

> **แยก 3 ระดับให้ชัดสำคัญมาก** เพราะโมเดลอาจผ่าน content แต่ตก dynamic
> (เขียนไทยเนียนแต่ทำนายผิด) ซึ่งเป็นคนละข้อสรุปกันโดยสิ้นเชิง

**7B — กัน leakage** (ถ้าไม่ทำ ผลทั้งหมดเป็นโมฆะ เพราะ LLM อาจ*จำ*คำตอบได้อยู่แล้ว)

| # | งาน |
|---|---|
| 7.1 | **Temporal cutoff** — กันไม่ให้ agent ดึงความจำที่ `timestamp > เวลาจำลองปัจจุบัน` |
| 7.2 | ใส่ข้อความในระบบ prompt กัน LLM ใช้ความรู้หลังวันที่กำหนด |
| 7.3 | กรอง bot / สแปม ก่อนเข้า ingestion |
| 7.4 | **Config snapshot** — บันทึก model, seed, prompt version, จำนวน agent ทุก run |
| 7.5 | **Validation กับข้อมูลจริง** — เทียบผลจำลองกับ**ผลโพลสำรวจความเห็น** (เช่น NIDA Poll / สวนดุสิตโพล) ของเหตุการณ์ที่เกิดขึ้นจริงแล้ว ไม่ใช่เทียบกับยอด engagement |
| 7.6 | เขียน `EXPERIMENTS.md` บันทึกว่าแต่ละ run ตั้งค่าอะไร ได้อะไร |
| 7.7 | **ทดสอบว่าโมเดลจำเหตุการณ์ได้อยู่แล้วหรือเปล่า** — ถามโมเดลตรง ๆ ว่ารู้ผลของเหตุการณ์ที่จะจำลองมั้ย ถ้ารู้ ต้องรายงานไว้ในข้อจำกัด |
| 7.8 | **Baseline ที่ต้องชนะ** — เทียบกับ (ก) เดาตามสัดส่วนตั้งต้น (ข) agent ชั้นเดียวไม่มี `expression_filter` ถ้าชนะไม่ได้ แปลว่าโครงสร้างสองชั้นไม่ได้ช่วยอะไร |

**เกณฑ์ผ่าน:**
- ใส่ความจำวันที่ในอนาคต → ต้องดึงไม่ได้
- รัน 2 ครั้งด้วย seed+config เดียวกัน → ผลลัพธ์เหมือนกัน
- **จำลองเหตุการณ์ในอดีต 1 เคส แล้วทิศทางความเห็นตรงกับผลโพลจริง** (ไม่ต้องตรงเป๊ะ แต่ทิศทางและลำดับต้องตรง)
- **ชนะ baseline ทั้งสองตัวใน 7.8** ไม่งั้นข้อสรุปของ O1 อ่อนมาก

## Phase 8 — Report Layer

**เป้า:** รายงานที่อ้างอิงกลับไปหาหลักฐานในการจำลองได้ (*auditable* ตาม O3)

แต่เมื่อยึด D11 แล้ว report layer เป็นส่วนหนึ่งของเปลือกแอปที่ต้องเดินได้อยู่แล้ว

**อย่าเขียนใหม่** — `backend/app/services/report_agent.py` มี ReAct agent +
`trace_statistics` ที่ทำงานได้แล้ว และ `report.py` มี `agent-log` / `console-log`
(พร้อม stream) ซึ่ง**คือ audit trail ที่ O3 ต้องการ**อยู่แล้ว

| # | งาน |
|---|---|
| 8.1 | ให้ `trace_statistics` อ่านชั้น `private_stance` จาก `action_args` (แก้ฟังก์ชันไปแล้ว เหลือต่อข้อมูลจริง) |

| 8.3 | ทุกข้อความในรายงานต้องชี้กลับไปที่ `actions.jsonl` บรรทัดไหนได้ |

เนื่องจาก openai 1.x/2.x ชนกัน (D2) ให้ทำเป็น **service แยก venv** คุยกันผ่าน `actions.jsonl` ไม่ต้อง import ข้ามกัน

```text
✅P0 ──→ ✅P1 ──→ ✅P2 ──→  P3   ──→  P4   ──→  P5   ──→  P6   ──→  P7   ──→ P8
 รันได้   โมเดลคน  RAG ไทย  ข้อมูล   ประชากร  เครือข่าย เสียบแอป  วัดจริง   รายงาน
                            (O2)                          (O3)    (O1,O4)
```

**ลำดับที่ห้ามสลับ:**

- **Phase 1 ก่อน Phase 4** — ถ้ายังไม่ได้แยก `private_opinion`/`public_expression` และยังไม่มี `media_access` การสร้างประชากรจะได้ persona ที่ผิดโครงสร้าง ต้องสร้างใหม่ทั้งชุด
- **Phase 2 ก่อน Phase 3** — ถ้ายัดคลังข้อความเข้า ChromaDB ด้วย embedding อังกฤษ แล้วค่อยเปลี่ยน ต้อง re-index ใหม่หมด
- **Phase 3 ก่อน Phase 4** — persona ที่ "อ่านเป็นคนไทยจริง" ต้องมีคลังภาษาไทยจริงเป็นฐาน ไม่งั้นได้ภาษาแปล
- **Phase 3 ก่อน Phase 7** — content correspondence ต้องมีคลังจริงไว้เทียบ
- **Phase 4 ก่อน Phase 5** — เครือข่ายสร้างจากคุณสมบัติของประชากร

**ทำคู่ขนานได้:** Phase 6 (เสียบ engine เข้าแอป) ไม่พึ่ง Phase 3 เลย — ถ้าติดเรื่องกฎหมาย/แหล่งข้อมูลใน Phase 3 ให้ข้ามไปทำ Phase 6 ก่อนได้ จะได้เห็นระบบเดินครบ flow เร็ว
